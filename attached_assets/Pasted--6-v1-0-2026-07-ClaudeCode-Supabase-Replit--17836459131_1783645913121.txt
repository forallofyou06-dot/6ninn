1. 目的・背景
現代版の「つながる会議（偶然の6人）」を、一部の幹事の力技ではなく仕組みで自走させる運営アプリ。
循環: ホストがテーマを立てて少人数の会を企画 → 社員が申し込み → 開催 → 写真1枚と口コミを残す → それを見た次の人が「面白そう」と参加する。
狙い: 「自然に孤独を減らす」「知らない部署の人と安心して少しだけ近づける」。テーマ設定が肝（効用そのものを目的に掲げない）。
ゴール: トライアルで設計を確かめ、発案者がいなくなっても回り続ける形にする。
「事務局はいない。みんなで作る」という思想（ルール10か条 九）を、アプリの設計にも反映する（重い管理者運用を作らない）。
2. トライアルの前提とスコープ
期間・規模
トライアル: 8〜12月（最初の10回程度は告知〜開催に最低1か月のラグがある前提）
検証: 翌1〜3月／正式リリース: 4月
規模: ホスト10名前後、1会あたり6名以内、まず「6人×5セット」程度。開始フロアは本社8・10・11F。
トライアルでやること（MVP）
企画の一覧・詳細・作成・申し込み・キャンセル
開催後レポート（参加者の感想・いいね／ホストの写真1枚＋報告）
マイページ（参加/主催履歴・興味タグ・つながり数）
お知らせ（アプリ内通知）
ルール10か条ページ
ご意見箱（事務局への一言）
事務局ビュー（隠しページ：KPIダッシュボード＋CSV書き出し＋ご意見箱閲覧）
あえてやらないこと（スコープ外）
アプリ内決済・会費徴収 → 当日現地精算（決済を入れない）。
複雑な抽選 → 先着のみ。
店の自動予約・在庫連携 → ホストが手で予約（リンクを貼る）。
深いTeams/SNS連携、多言語対応、凝った権限管理、通報機能。
ネットワーク遮断（社内IP/VPN限定）→ トライアルは行わない（URLを知る人は誰でもアクセス可）。
3. 利用者と権限（ロール）
ロール
誰
できること
member（一般社員）
登録した社員
一覧閲覧・申し込み・キャンセル・自分の参加会でレポート/いいね・マイページ・ご意見箱投稿
host（ホスト）
会を立てる人（誰でもなれる）
member権限＋企画作成・自分の会の編集・開催者報告
office（事務局）
芝尾・古沢さんら数名
member権限＋事務局ビュー（KPIダッシュボード・CSV書き出し・ご意見箱閲覧）。※他人の会の代理編集・削除はしない
maintainer（メンテ）
コード・インフラを触る人（3名）
GitHub/DB/デプロイ。アプリ内権限とは別レイヤー
確定事項
ホストは誰でもなれる運用でスタート。
会の削除・修正は本人（ホスト）が行う。事務局は代理編集・削除をしない。
事務局ビューは隠しページ（一般導線からは見えない／office権限のみ到達可能）。
運用体制（プロトタイプ時）: 企画統括＝小売DX推進部 芝尾・古沢／アプリ作成＝小売DX推進部 山本・古沢、DX推進部 坂上／組合＝金子／フロアアンバサダー＝8F鈴木（リーダー）・10F天田・11F／ファーストホスト＝各取締役。
4. 主要機能の要件（画面ごと）
4-1. 企画一覧（トップ）
タグ（#食 #韓国 #猫 #歴史 など）で絞り込み・検索。
各カード: テーマ／日時／場所／会費／残席（例「あと1席」）。
並び順: デフォルトは新着順。可能なら並び替え（開催が近い順／残席わずか順）を付ける。
終了した会は別タブで一覧化（レポートを見せて次の参加を促す）。
4-2. 企画詳細
表示: テーマ／サブテーマ／日時／場所（食べログ等リンク可）／会費／ホスト／定員／その他注意事項／最低実行人数／募集締め切り日／ルール（6人以内・2時間以内・5,000円以内）。
「この席に申し込む（先着）」ボタン。残席と "あなたの席が空いています" の演出（実残席を表示。「常に1席空けておく」演出は今回見送り）。
定員はホストを含む（ホスト1＋参加5＝計6 が上限）。
申し込み時に取る情報: 氏名・所属（自動）＋任意のひとことコメント。
4-3. 企画作成（ホスト）
入力: テーマ／サブテーマ（例「Seoulの楽しみ方 × 韓国料理」）／タグ／開催日時／開催場所＋リンク／会費／定員／その他注意事項／最低実行人数／募集締め切り日。
バリデーション: 人数は6人固定上限（3〜6で設定可）、時間2時間以内、会費5,000円以内（ホストが金額設定）。
テーマは完全に自由入力。タグも自由作成可。
補足表示（注意書き）: 「開催日の1か月前を目安に登録」「最低実行人数に満たない場合は自動的に未実施」。
場所の予約はホストが行う（先に押さえても、締切後に予約してもホストの自由）。運用上の注記としてアプリに明記。
4-4. 企画申し込み・キャンセル
先着で定員到達したら締切。
キャンセル挙動:
募集締め切り日前: アプリからキャンセル可。空いた席は先着で再び埋められる（一覧の残席が戻る）。
募集締め切り日後: アプリからはキャンセル不可。緊急時はホストに直接連絡（アプリ外）。締切後キャンセルの会費は本人負担（受渡はホストと直接）。
1人あたりの同時参加数・同時主催数の上限は設けない。
4-5. 終了後レポート（参加者）
参加者が感想（ひとこと）と、いいねを残せる。実名。
公開範囲は全社員。掲載期間は設けない。
4-6. 開催者報告（ホスト）
ホストが写真1枚（必須）＋簡単な報告を投稿（スマホから1枚アップロード）。
公開範囲・保存期間は設けない。
4-7. マイページ
プロフィール: 氏名・所属（部署／フロアを自由入力）・興味タグ。
参加履歴・主催履歴・保存した会。
つながり数＝これまでの会で一緒になったユニークな人数（＋その人の一覧を表示）。
マイページ本体は本人のみ閲覧。他社員から見えるのは個人プロフィール（氏名・所属）のみ。
4-8. お知らせ / 通知（アプリ内のみ）
例: 「残り1席」「あなたの会に参加者（5/6人）」「口コミがついた」「今週の新着 #猫 の会が2件」「レポート公開」。
「今週の新着 #タグ」通知は、自分の興味タグに一致する新着を対象とする。
通知手段はアプリ内のみ（メール/Teamsはトライアルでは使わない）。
4-9. ルール10か条ページ
静的ページとして10か条を掲載（内容は巻末「参考: ルール10か条」）。
4-10. ご意見箱
どこからでも送れる自由記述の意見箱（＝事務局への一言）。任意で「どの会について」を紐づけられる。
届き先は事務局ビュー（4-11）。
4-11. 事務局ビュー（office・隠しページ）
KPIダッシュボード（7章）。
データのCSV書き出し（会・参加・レポート・タグ・KPI）。
ご意見箱の一覧・閲覧。
※会の代理編集・削除機能は持たない。
5. データ設計の方針
主要テーブル
users（id / メール / 氏名 / 所属 / role[member/host/office/maintainer] / 興味タグ / 作成日時）
events 企画（id / host_user_id / テーマ / サブテーマ / タグ / 開催日時 / 場所 / 場所リンク / 会費 / 定員 / 最低実行人数 / 募集締め切り日 / その他注意事項 / 状態[募集中/実施確定/未実施/開催済] / 作成日時）
participations 参加（id / user_id / event_id / 状態[申込/キャンセル] / 申込日時 / キャンセル日時）
reports レポート（id / event_id / author_user_id / 種別[参加者感想/開催者報告] / 本文 / 写真URL / 作成日時）
likes（user_id / target種別[report/event] / target_id）
tags / event_tags（多対多）／ ユーザー興味タグは users 側に保持
notifications（id / user_id / 種別 / 本文 / 既読 / 作成日時）
feedbacks ご意見箱（id / from_user_id / 本文 / event_id[任意] / 作成日時）
派生・集計（テーブルに持たず算出でよい）
残席 = 定員 −（申込状態の participations 数）
つながり（個人）= 自分が「開催済」の会で同席した相手のユニーク集合
つながり延べ数（全体KPI）= 各「開催済」会の参加人数 n について n×(n−1)/2 を合計
6. 会のライフサイクル（状態遷移）
募集中: 作成直後。定員まで先着受付。締切前キャンセルで残席が戻る。
募集締め切り日を過ぎたら判定:
参加者数 ≥ 最低実行人数 → 実施確定
参加者数 < 最低実行人数 → 未実施（自動中止）
開催日時を過ぎた「実施確定」→ 開催済（レポート/写真の投稿対象になる）。
「募集締め切り日」は募集・実施判定を兼ねる単一の日付。
7. KPI・データ取得
主KPI（全体）: つながり延べ数 = 各会のペア数 n×(n−1)/2 の累計（複利的に伸びる想定）。
個人指標: つながり数（ユニーク同席人数）。
あわせて取得・可視化: 開催数／参加率／どのタグ・価格帯で集まった/集まらなかったか／閲覧数／いいね数／感想数／募集締切〜開催のリードタイム。
事務局ビューで一覧・グラフ表示し、CSV書き出し可能に。
8. ログイン・アカウント
登録: 社員が自分で登録（自己サインアップ）。
方式: パスワードを持たないメールのマジックリンク（メアド入力→届いたリンクで認証）。※非エンジニア運用で問い合わせ負荷を下げるため。
ドメイン: 社内メールドメインは必須にせず推奨（登録画面に「社内メールでの登録を推奨」の注意書きを出す。テスト段階のため本人の自由意思で登録可）。
初回ログイン後、マイページ基礎情報（氏名・所属・興味タグ）を登録する導線。
9. 非機能・運用
対応デバイス: スマホ優先（社内PCブラウザでも閲覧可）。日本語のみ。
ホスティング/公開: トライアルはURLを知る人は誰でも到達可でOK（アプリのログインで実質的に運用者に閉じる）。ネットワーク遮断はしない。
バックアップ/可用性: 複数人が使い始めたら自動バックアップのある構成に（Supabaseなら無料枠は自動バックアップなし＆7日無操作で自動停止のため $25/月Proが無難）。
データガバナンス: 氏名・所属・"誰と誰が会ったか"を扱う。本番拡大前に情報システム部門の確認、組合にも共有。データ所在（海外クラウド）を確認。退職者データの扱いはトライアルでは特段の処理をしない。
数名運用の権限分離: コードはGitHub、データはDB、アプリ内はoffice権限、と層で分ける。コードを触るのはmaintainer 3名に限定。
10. 開発の進め方（フェーズ）
Phase 0: データモデル（5章）＋マジックリンク・ログイン＋プロフィール登録。
Phase 1: 企画一覧＋企画作成（作って一覧に出るまで）。
Phase 2: 企画詳細＋申し込み・キャンセル＋会のライフサイクル判定＋マイページ。
Phase 3: 開催後レポート＋写真＋いいね＋お知らせ（アプリ内通知）。
Phase 4: 事務局ビュー（隠しページ・KPI・CSV・ご意見箱）＋ルール10か条ページ。
依頼のコツ（非エンジニア向け）
フェーズ単位で頼み、動いたら画面で確認してから次へ。
変更のたびに履歴を残す（GitHub / Replitのチェックポイント）＝壊れても巻き戻せる。
role（member/host/office）は最初の設計に必ず含める（後付けは面倒）。
11. 用語・早見表
定員: ホストを含む上限人数（3〜6）。
募集締め切り日: 単一の締切日。ここで実施確定／未実施を自動判定。
最低実行人数: これ未満なら未実施（自動中止）。
つながり数（個人）: 同席したユニーク人数。
つながり延べ数（全体KPI）: 各会 n×(n−1)/2 の累計。
office（事務局）: KPI・CSV・ご意見箱を見られる隠しビュー。代理編集はしない。
